# Codex Architecture Governor

一个可复用的 Codex 架构治理 skill。

它帮助 Codex 更好地处理：

* 模块边界
* 组件职责
* 状态归属
* 依赖方向
* 代码放置位置
* 架构契约
* 可维护性
* 可执行的架构防线

它不会强迫每个项目采用同一种目录结构，而是引导 Codex **检查仓库、理解现有架构、识别职责和边界，再为当前项目选择合适的结构**。

## 为什么需要它

编码 agent 很擅长让功能跑起来，但不一定同样擅长保护代码库的长期结构。

没有明确的架构指导时，一连串看似合理的修改可能逐渐把所有职责塞进一个入口文件：

```text
App.tsx
├── 路由
├── 认证
├── API 请求
├── 仪表盘状态
├── 表单校验
├── 对话框
├── 设置
├── 事件处理
└── 800 行 JSX
```

每次修改单独看都可能合理，但最终的代码库并不合理。

常见的应对方式是增加以下模糊规则：

```text
保持组件小巧。
使用整洁架构。
拆分大文件。
遵循最佳实践。
```

这些规则过于模糊，无法稳定地改变 agent 的行为。

另一个极端是强迫所有项目使用固定结构：

```text
controllers/
services/
repositories/
hooks/
components/
utils/
```

这往往会制造不必要的抽象，让小项目更难维护。

**Codex Architecture Governor 采用另一种方式。**

它治理的是**架构决策过程**，而不是规定一个通用架构。

## 核心思路

这个 skill 遵循以下流程：

```text
检查
  ↓
分类
  ↓
识别职责归属
  ↓
识别边界
  ↓
选择结构
  ↓
持久化架构契约
  ↓
实现
  ↓
检查架构一致性
  ↓
加固重复出现的违规
```

目标不是：

> 让代码看起来像企业级项目。

目标是：

> 在代码库开始漂移之前，明确职责、边界、依赖方向和变更成本。

## 设计原则

### 架构是职责归属，不是文件夹

skill 首先会询问：

```text
谁负责这段行为？
谁负责这份状态？
谁负责这份数据？
哪些模块可以互相导入？
什么是公开接口？
读者自然应该在哪里找到这段行为？
```

目录结构应当在这些问题之后决定。

### 保持入口文件轻薄

应用入口，例如：

```text
App.tsx
page.tsx
main.ts
路由处理器
```

主要负责组合和接线，不应逐渐成为以下内容的默认归属者：

* 特定功能的业务规则
* 无关的状态
* 数据获取
* 工作流逻辑
* 表单校验
* 多个相互独立的 UI 领域

大入口文件是架构异味，但不自动等于架构违规。

### 按职责拆分，而不是按行数拆分

本项目刻意避免这样的规则：

```text
组件超过 300 行 → 必须拆分
```

代码行数可以作为信号，但不是架构决策本身。

更有意义的拆分信号包括：

* 存在多个独立的变更原因
* 存在多个职责拥有者
* 混合了无关的领域概念
* 业务逻辑与展示逻辑混在一起
* 数据访问与可复用 UI 混在一起
* 存在独立的演进路径
* 测试边界不清楚
* 跨功能直接访问内部实现

一个内聚的 500 行解析器可能没有问题；一个同时包含认证、API 请求、对话框状态、路由和表单校验的 180 行 `App.tsx`，已经可能存在职责归属问题。

### 优先局部，基于证据再共享

代码应当靠近拥有它的功能或工作流。

只有在有实际证据表明某段代码拥有稳定的跨功能契约时，才应将它提升到 `shared`。

不要为假设中的未来复用提前构建抽象。

### 一个规范拥有者

skill 会避免重复拥有同一状态，例如：

```text
服务端数据
→ 本地状态
→ Effect 同步
```

或：

```text
store A
↔ 同步 Effect
↔ store B
```

只要可能，状态就应有一个清晰且唯一的规范拥有者。

### 尊重现有架构

这不是只适用于绿地项目的架构生成器。

面对已有仓库，默认做法是：

```text
理解当前架构
→ 找出价值最高的接缝
→ 增量改进
```

而不是：

```text
用偏好的架构替换整个仓库
```

## 工作模式

这个 skill 有四种架构参与级别。

### Lightweight（轻量）

适用于以下简单变更：

* 文案修改
* 仅样式修改
* 简单重命名
* 独立 bug 修复
* 静态资源替换

不需要额外的架构仪式。

### Design（设计）

适用于尚未建立架构的场景，例如：

* 新应用
* 新服务
* 大型新功能区域
* 新包或领域模块

skill 会确定：

* 职责归属
* 模块边界
* 依赖方向
* 状态归属
* 公开接口
* 项目结构

### Deepen（深化）

适用于应用能够运行，但架构已经变得难以修改的场景。

常见信号包括：

* 巨型入口文件
* 重复的业务规则
* 功能之间直接导入内部实现
* 状态归属不清
* `shared/` 变成杂物间
* UI 直接访问基础设施
* 多个概念职责重叠

目标不是重写，而是找出高价值的架构接缝，一次迁移一条完整的垂直切片。

### Harden（加固）

适用于架构已经明确，但仍然反复被违反的场景。

此时会在合适的地方把架构意图转化为可执行检查，例如：

```text
导入边界规则
依赖环检测
包导出限制
死代码检查
架构脚本
CI 门禁
```

只有重要且能够机械验证的规则，才应升级为硬检查。

## 架构契约

对于非简单仓库，skill 可以维护一个项目级架构契约，例如：

```text
docs/ARCHITECTURE.md
```

这份文档是仓库的架构事实来源，通常包含：

```text
系统形态
模块及其职责
依赖方向
入口点
状态归属
数据访问
模块公开接口
共享代码提升规则
测试边界
架构防线
已知例外
架构决策
```

全局 skill 定义**如何做架构决策**；`ARCHITECTURE.md` 记录**特定仓库的决策结果**。

## 与 AGENTS.md 集成

`AGENTS.md` 应保持简短，不要重复整个架构规范，而是指向架构契约：

```text
对于非简单实现：

- 修改模块边界前先阅读 docs/ARCHITECTURE.md。
- 遵守模块公开接口和依赖方向。
- 不要引入跨功能的内部导入。
- 如果请求与架构契约冲突，要明确指出冲突，不要静默绕过。
- 运行所属包定义的架构检查。
```

这种方式也适用于 monorepo，例如：

```text
/AGENTS.md
/apps/web/AGENTS.md
/services/core/AGENTS.md
```

## 组件职责

仓库级架构只是问题的一半。

在一个功能内部，Codex 仍需要判断：

```text
谁负责这份状态？
这个处理器应该放在哪里？
谁应该获取这份数据？
这个包装器是否真的需要？
这个 Effect 是真实的副作用，还是职责归属错误？
```

因此，skill 也提供组件级职责指导。

### 状态

默认规则：

> 把状态保留在最低层级的有意义拥有者上。

只有在以下情况下才向上提升：

* 兄弟组件需要同一个事实来源
* 父级负责协调整个工作流
* 需要有作用域的持久化
* 状态确实是跨功能的

### 远程状态

避免不必要的重复：

```tsx
const query = useQuery(...)

useEffect(() => {
  setItems(query.data)
}, [query.data])
```

除非本地状态有独立的语义，例如可编辑草稿，否则不应复制远程状态。

### URL 状态

路由标识、筛选条件和搜索参数通常已经有天然拥有者：

```text
URL
```

避免同时在以下位置维护同一个规范值：

```text
URL
+
全局 store
+
组件状态
```

### Effects

优先：

```text
在渲染过程中派生
```

或：

```text
在触发变化的事件中处理
```

Effect 主要用于与外部系统同步。

### 包装器

包装器通常应该拥有真实契约，例如：

* 行为
* 校验
* 状态
* 领域语义
* 无障碍行为
* 稳定的视觉语义

单纯转发 props 的包装器通常只会增加导航成本，而不会改善架构。

## 可执行的架构防线

对于反复违反的规则，仅靠文档并不够。

项目采用以下加固梯度：

```text
文档
    ↓
警告
    ↓
静态检查
    ↓
测试
    ↓
CI 门禁
```

只有重要且能够机械验证的规则，才应成为硬检查，例如：

* 跨功能内部导入
* 禁止的依赖方向
* 循环依赖
* 包边界违规
* 未使用的文件和导出

文件大小刻意只作为**警告信号**，不是普适的硬门禁。

## 安装

将 skill 复制到 Codex skills 目录：

```bash
mkdir -p ~/.codex/skills
cp -R ./engineering-architecture ~/.codex/skills/engineering-architecture
```

然后按当前环境重启或重新加载 Codex。

如果希望将 skill 与项目放在一起，也可以采用仓库内安装方式。更多安装说明见 [INSTALL.md](../INSTALL.md)。

## 示例

没有架构治理时：

```text
用户：
添加认证、设置和仪表盘。

Agent：
修改 App.tsx。
```

使用本 skill 后：

```text
检查仓库
↓
判断应用规模
↓
识别认证、仪表盘、设置等独立能力
↓
确定状态和数据归属
↓
让 App.tsx 保持为组合根
↓
把行为放入对应功能
↓
定义模块公开接口
↓
实现垂直切片
↓
检查架构一致性
```

一种可能的结果是：

```text
src/
  app/
    App.tsx
    providers/
    router/

  features/
    auth/
    dashboard/
    settings/

  shared/
    ui/
    lib/
```

但这个目录结构**不是 skill 硬编码的结果**。另一个项目完全可能合理地采用不同架构。

## 这个项目不是什么

它不是：

* 通用的 Clean Architecture 模板
* 固定的 React 文件夹规范
* 文件大小检查器
* 组件生成器
* 把所有内容拆成小文件的要求
* 到处引入 repository、factory 和 adapter 的借口
* 对项目级架构决策的替代品

它是一个架构**治理器**：让架构决策明确、一致，并在适当时可执行。

## 当前范围

第一版重点覆盖：

* TypeScript
* React
* Vue
* Node.js
* 模块职责
* 组件职责
* 状态归属
* 架构契约
* 架构漂移
* 基础可执行架构防线

未来的 profile 可能包括：

* Electron
* monorepo
* 全栈应用
* 后端服务
* 微前端
* 数据可视化应用

这些内容会根据真实项目需求增加，而不是为了理论上的完整性提前加入。

## 校验理念

成功不由以下指标衡量：

```text
创建了多少文件
引入了多少层
目录树看起来多么“企业级”
```

成功体现在 Codex 是否能够：

* 保持清晰的职责归属
* 尊重现有架构
* 避免巨型默认拥有者
* 避免过早抽象
* 保持易理解的依赖方向
* 找到有意义的重构接缝
* 把重复出现的架构违规转化为防线

这个 skill 应当在不为简单项目过度设计的前提下，改善结构混乱的仓库。

## 贡献

欢迎贡献，尤其是：

* 真实世界的失败案例
* 架构评估场景
* 面向特定框架的 profile
* 依赖边界工具
* 过于激进的架构规则导致的误报
* skill 应当有意少做一些的案例

提议新的通用规则时，请提供它能够适用于多种项目类型的证据。

项目特定的偏好通常应成为 profile 或 reference，而不是全局要求。

## 理念

编码 agent 不应该需要一段巨型提示词，逐个规定每个文件应该放在哪里。

它们应该能够：

```text
理解代码库
识别职责归属
推理边界
做出架构决策
持久化决策
并长期保护这些决策
```

这就是本项目要解决的问题。
